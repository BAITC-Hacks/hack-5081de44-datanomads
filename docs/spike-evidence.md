# Проверка правил всплеска на двух региональных CSV

Скрипт [`evaluate_spike_csv.py`](../scripts/evaluate_spike_csv.py) использует
только локальные даты создания и считает обращения за день. ВКО и Алматинская
область — данные заказчика, но в файлах нет исходного текста обращения и
подтверждённых incident labels. Это исследование суммарной дневной нагрузки
каждой области, без разбивки по утверждённым темам и без почасовой проверки.

Для каждого дня после первых восьми недель оцениваются восемь предыдущих
значений того же дня недели. Простой baseline сравнивает текущее число с
медианой через ratio; сезонный robust score использует медиану и MAD.
Проверены три порога каждого метода при минимуме 20 обращений в день.
Cooldown в семь дней посчитан отдельно. Это сетка чувствительности, а не
утверждённые параметры detector.

| Выгрузка | Дней оценки | Ratio 2.0: сырых / с cooldown | Robust z 4.0: сырых / с cooldown |
| --- | ---: | ---: | ---: |
| ВКО | 975 | 89 / 41 | 69 / 32 |
| Алматинская область | 259 | 18 / 11 | 12 / 8 |

Все шесть конфигураций и 20 агрегатных дат для проверки приведены в
[`vko_109_spike_exploration.json`](../data/reports/vko_109_spike_exploration.json)
и [`almaty_109_spike_exploration.json`](../data/reports/almaty_109_spike_exploration.json).
Очереди имеют статус `PENDING`: ни одна дата не подтверждена как настоящий
инцидент или ложное срабатывание. Поэтому precision, recall и
time-to-detect остаются `null`, порог для runtime не выбран.

Дни без строк в CSV считаются ненаблюдаемыми. ВКО исключены четыре дня,
которые затронули два пропуска дат и неполную историю того же дня недели.
Исходные CSV и персональные поля не копируются в отчёты или Git.
Для калибровки `region × topic × time` нужны проверенная тематическая
разметка, полнота временного ряда и человеческая проверка инцидентов.

## Полная очередь для проверки

`review_queue` в исследовательских отчётах содержит только 20 дат с наибольшим
`robust_z`. Этот срез нельзя использовать для оценки precision: он пропускает
часть срабатываний и смещён в сторону наиболее заметных всплесков.

Для локального CSV можно создать полный агрегатный список дат, которые
сработали хотя бы по одному из шести проверяемых правил:

```bash
python scripts/export_spike_review.py /path/to/local-export.csv --output /tmp/spike-review.json
```

Экспорт содержит SHA-256 входного CSV, даты, дневные количества, параметры
правил и признак срабатывания после cooldown. Он не содержит исходные строки
CSV или текст обращений; файл с результатом следует хранить вне Git.
Каждая дата имеет статус `PENDING`. Для precision нужно проверить все
срабатывания выбранного правила. Для recall нужен независимо составленный
реестр подтверждённых инцидентов с датами начала и конца и подтверждённой
полнотой охвата всего оценочного периода, включая дни без срабатывания.
Требования к этому реестру записаны в `incident_ground_truth_requirements`.
Пока его нет, `precision`, `recall`, `false_alerts_per_period` и
`time_to_detect` остаются `null`, а `runtime_eligible=false`.

## Проверка по независимому реестру инцидентов

`export_spike_review.py` выдаёт формат `spike-review-candidates.v2` со списком
**всех оценённых дат**, включая даты без срабатываний, и SHA-256 этого списка.
Новый экспорт нужен для вычисления метрик; старые очереди `v1` оценщик
отклоняет. Реестр составляет проверяющий независимо от детектора. Он должен
содержать ровно одну подтверждённую запись `daily_labels` для каждой даты из
`evaluated_dates`, а также все подтверждённые интервалы инцидентов. Пустой
`incident_ids` означает проверенный день без инцидента. Неотмеченные дни
нельзя автоматически считать отрицательными примерами.

```json
{
  "schema_version": "spike-incident-registry.v1",
  "source_sha256": "<source_sha256 из очереди>",
  "scope": "total_daily_appeals_in_one_export",
  "unit": "one_region_total_per_day",
  "evaluated_date_sha256": "<evaluated_date_sha256 из очереди>",
  "candidate_report_sha256": "<SHA-256 байтов файла очереди>",
  "coverage_assertion": {
    "all_evaluated_dates_reviewed": true,
    "independent_of_detector": true,
    "reviewer_id": "reviewer-7",
    "reviewed_at": "2026-09-27T12:00:00+00:00"
  },
  "daily_labels": [
    {"date": "2025-01-01", "incident_ids": [], "review_status": "CONFIRMED"}
  ],
  "incidents": [
    {"incident_id": "I-1", "onset_date": "2025-01-02", "end_date": "2025-01-03", "review_status": "CONFIRMED"}
  ]
}
```

Пример показывает поля, а не полный реестр: в настоящем файле нужны все
оценённые даты, а `incident_ids` каждого дня должен совпадать с интервалами
из `incidents`. Перекрывающиеся интервалы и интервалы с ненаблюдаемой датой
отклоняются для суммарного дневного ряда одной области. SHA-256 файла очереди
можно получить через `sha256sum /tmp/spike-review.json`. Проверяющий явно
подтверждает полноту охвата и независимость разметки от срабатываний.

```bash
python scripts/evaluate_spike_incidents.py /path/to/local-export.csv /tmp/spike-review.json /path/to/incident-registry.json --output /tmp/spike-incident-evaluation.json
```

Оценщик заново строит очередь из исходного CSV и требует полного совпадения
с переданной очередью. Затем сверяет SHA-256 файла очереди, источник,
единицу, SHA-256 списка дат, полный набор дней и непротиворечивость
интервалов. Для каждого из шести правил он считает
`precision` по сигналам **после cooldown**, `recall` по подтверждённым
инцидентам, число ложных сигналов на 30 оценённых дней и задержку от начала
инцидента до первого сигнала в днях. `recall=null`, если подтверждённых
инцидентов нет; задержка `null`, если ни один не обнаружен. Ложные даты
выводятся для повторной проверки. Метрики относятся только к оценённым
дням одной области и суммарным обращениям: они не доказывают качество для
`region × topic × time`. Оценщик не выбирает порог и оставляет
`runtime_eligible=false`. Сейчас подтверждённого реестра нет, поэтому
метрики реальных выгрузок не вычислены.
