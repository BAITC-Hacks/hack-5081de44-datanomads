Источник: предоставленный локально CSV «Обращения граждан 109 — Восточно-Казахстанская область».
Сырой файл не хранится в репозитории. Его SHA-256:
`bfa29295829a3c7830ffa5d0389a2924676f804464e577931d98bf3d8ffa7716`.
Условия использования и публикации исходного набора пока не подтверждены.

В `region` обычно указаны город или район внутри одной области: 82 502 записи
относятся к Усть-Каменогорску. Это не покрытие 20 регионов из ТЗ. Некоторые
служебные значения выглядят смещёнными; автоматическая проверка длины нашла
одно значение `region` длиннее 120 символов. Перед импортом нужен отдельный
quality gate для допустимых значений и ручная проверка исключений.

CSV не содержит отдельного поля исходного текста обращения или метки языка.
Заказчик подтвердил, что `com_exp` не является пригодным исходным текстом
обращения; оно заполнено только в 2% записей. Синтетические тексты созданы
отдельно и не восстанавливают тексты этих строк. `category` — исходная категория, а не
утверждённая метка для 10+ классов Pulse. Поля `service` и `contractor` нельзя
считать официальным правилом маршрутизации без проверки их значения у источника.
В файле есть персональные поля; имена, адреса и тексты не выводятся в отчёт и
не должны попадать в Git или внешний LLM.

## Применение и границы

Исторические даты и категории дают основу для **локальной проверки** динамики,
детектора всплесков и прогноза нагрузки этой области. Для этого требуется
агрегация с проверкой качества строк. Файл нельзя напрямую загрузить как
`UnifiedTicket`: контракт требует `original_text`. Из него нельзя честно
обучить и оценить текстовый classifier или embedding model, подтвердить качество
на казахском и русском языках либо заявить покрытие 20 регионов.

Для прототипа остаётся отдельно помеченный синтетический корпус. Он проверяет
пользовательский сценарий и воспроизводимость, но не заменяет реальные held-out
метрики, требуемые ТЗ и материалами заказчика.

## Проверка прогноза по реальной истории

На дневном числе обращений выполнен rolling backtest недельного сезонного
базового прогноза. Перед каждой точкой прогноза требуется не менее 365
последовательных наблюдаемых дней; новые точки выбираются каждые 30 дней. Каждый
прогноз строится только по дням до своей точки отсчёта. Даты 2023-01-13 и
2023-01-14 без строк считаются ненаблюдаемыми, а не нулевыми. Окна без 365
последовательных наблюдаемых дней истории или полного горизонта исключены;
календарный шаг точек прогноза сохранён.

| Горизонт | Окон | MAE, обращений/день | WAPE |
| --- | ---: | ---: | ---: |
| 30 дней | 21 | 40,94 | 47,42% |
| 60 дней | 20 | 39,03 | 46,61% |
| 90 дней | 19 | 39,06 | 47,07% |

Это оценка **простого baseline** на общем объёме одной области, а не качество
обученной модели, не оценка по категориям или 20 регионам и не сквозной тест
работающего API. Ошибка около 47% по WAPE не даёт оснований заявлять точный
прогноз для заказчика. Полные агрегатные метрики включают RMSE и sMAPE:

```bash
python3 scripts/evaluate_forecast_csv.py '/path/to/export.csv' \
  --output /tmp/pulse109-forecast-evaluation.json
```

Скрипт выводит только даты, счётчики, метрики и SHA-256 исходного файла; строки
CSV и персональные поля не сохраняются. Чтобы улучшать прогноз без самообмана,
нужны проверка двух пустых дней, отдельный temporal holdout и сравнение с
простыми альтернативами на той же выборке.

Повторить безопасный агрегатный аудит без копирования исходного файла в репозиторий:

```bash
python3 scripts/data_audit.py '/path/to/export.csv' --output /tmp/pulse109-audit.json
```

Отчёт содержит только счётчики, даты, названия известных колонок и checksum.
Для выгрузки Алматинской области есть отдельный
[разбор категорий](almaty-2025-taxonomy-review.md); его предложенные метки тоже
не являются утверждённой обучающей разметкой.
